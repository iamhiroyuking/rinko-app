初版の約60問は2026-08-10に全て決着し、[requirements.md](requirements.md) と

以下は、**データベーススキーマを書く過程で新たに見つかった**論点。
「個人の状態」と「共有の状態」の混同が原因のものが多い。

---

## 解決済み

| 論点 | 結論 |
|---|---|
| 課題「全員が理解できているか分からない」への対応 | 運用してから判断する。まずは返信で質問できる形で使う |
| 全員が教材を完全削除した後のデータ | データベースから削除する（`delete_orphan_book()` として実装） |
| リアルタイム更新の方式 | 画面遷移時に再取得し、新着があれば通知して手動更新を促す |
| 本棚のステータスの置き場所 | **`Book` ではなく `Membership` へ移した。** 教材側に置くと、誰かが「学習済み」にした瞬間に共有相手全員のホームから消えてしまう |
| 招待リンクで参加できない問題 | リンクを受け取った人はまだ参加者ではなく `invite_links` を読めないため照合できなかった。`join_book_with_token()` を用意して解決 |
| 教材の作成者が自分の教材を見られない問題 | 閲覧の条件が「参加していること」なので、作成時に参加情報を作る必要があった。`handle_new_book()` として実装 |
| 新着通知に必要な既読状態 | `Membership.last_seen_at` を追加 |

## 未決（要回答）

詳細と選択肢は [features.md の「要検討」](features.md#要検討) にある。

| # | 論点 | 推奨 |
|---|---|---|
| Q1 | ログのマークは個人の栞か、全員に見える印か | 個人の栞（別テーブルへ移す） |
| Q2 | 回を削除したとき誰のゴミ箱に入るか | 全員のゴミ箱に出て誰でも復元できる |
| Q3 | 添付ファイルの保護方針 | 非公開バケット＋期限付きURL |
| Q4 | 第N回の番号が重複したときの並び順 | 作成日時が古い順 |

Q1・Q2はデータの持ち方が変わるので、スキーマを適用する前に決めたい。
Q3・Q4は実装時の判断で足りる。
