# 機能一覧（画面別）

実装すべき機能を画面ごとに全て並べたもの。
「なぜ作るか」は [requirements.md](requirements.md)、遷移は [screen-flow.md](screen-flow.md)、着手順は [issues.md](issues.md)。

## 表記

| 記号 | 意味 |
|---|---|
| 👤 | **個人の状態**。その人の画面の見え方だけが変わり、共有相手には影響しない |
| 👥 | **共有の状態**。参加者全員に影響する |
| ✏️ | `editor` のみ実行できる |
| ⚠️ | 未決。[要検討](#要検討) を参照 |

**設計の原則**: ある操作が「自分の画面の見え方」を変えるだけなら👤、「みんなのデータ」を変えるなら👥。
👤 の情報は `Membership` に置く。ここを間違えると、誰かの操作が共有相手全員に波及する。

## 全体で効くルール

### 権限

| 操作 | editor | viewer |
|---|---|---|
| 閲覧 | ○ | ○ |
| 回の作成・編集・削除 | ○ | × |
| ログの投稿・返信 | ○ | × |
| 回のステータス変更 | ○ | × |
| 招待リンクの発行 | ○ | × |
| 自分の投稿の編集・削除 | ○ | ― |
| 他人の投稿の編集・削除 | × | × |

作成者に特別な権限はない。`created_by` は記録として持つだけ。

### 削除

| 対象 | 挙動 | 実行できる人 |
|---|---|---|
| ログ・返信 | 確認ダイアログ → 完全削除。返信も連鎖 | 投稿者本人 |
| 教材 | 確認ダイアログ → ゴミ箱。自分の本棚から消えるだけで、共有相手には残る | 参加者各自 |
| 回 | 確認ダイアログ → ゴミ箱。全員の画面から消える | **作成者のみ** |
| ゴミ箱の中身 | もう一度削除で完全削除。復元も可能 | 上と同じ |

**共有されているものの扱い**は次のとおり。追加と編集は参加者全員で同期し、削除だけは作った本人に限る。
回を削除すると回そのものが無くなるので全員の画面から消えるが、ゴミ箱に出て復元できるのは作った人だけ。
作成者がその教材から抜けている場合は、誰も片付けられなくなるため編集者なら削除できる。

参加者が全員教材を完全削除した時点で、教材と配下のデータをデータベースから削除する。
教材を抜けた人が残したログは残る。同じ人が再参加すれば過去の発言と繋がる。

### 未対応の課題

要件定義に挙げた7つの課題のうち2つは、意図的に対応を見送っている。

- **「進度の目安・目標が立っていない」** — 目標ペース機能を廃止したため、進捗バーで現在地は見えるが「遅れているか」は見えない
- **「全員が理解できているか分からない」** — 理解度の意思表示もメンバーごとの復習回数も不採用。まずは返信で質問できる形で運用してから判断する

## データモデル

個人の状態と共有の状態の区別を明示したもの。詳細は [requirements.md](requirements.md)。

```
User        id, email, display_name
            ※ Supabase Auth の auth.users + profiles テーブル

Book    👥  id, title, cover_image_url, goal, created_by
            共有相手にも影響する情報だけを持つ

Membership  id, book_id, user_id, role
        👤  shelf_status, display_order, last_seen_at, deleted_at
            「その人の本棚がどう見えるか」に属する情報はすべてここ

InviteLink  id, book_id, token, role, created_by

Unit    👥  id, book_id, order, title, objective, presenter_id,
            scheduled_date, status, created_by, deleted_at
            created_by は削除できる人。編集は全員で同期する

Log     👥  id, unit_id, author_id, parent_log_id, type,
            title, body, page_start, page_end

LogMark 👤  log_id, user_id
            しおり。他人のマークは見えない

Tag     👥  id, book_id, name
LogTag  👥  log_id, tag_id
Attachment  id, log_id, file_url, file_name, mime_type
```

### データベース側に用意した仕組み

| 名前 | 役割 |
|---|---|
| `is_member()` / `can_edit()` | 参加・権限の判定。行レベルセキュリティの再帰を避けるため `security definer` にしている |
| `handle_new_user()` | サインアップ時に `profiles` を作る |
| `handle_new_book()` | 教材を作った人を自動で参加者にする。これが無いと本人が自分の教材を見られない |
| `join_book_with_token()` | 招待リンクでの参加。受け取った人はまだ参加者ではなく `invite_links` を読めないため、関数越しに参加させる |
| `delete_orphan_book()` | 参加者が誰もいなくなった教材を削除する |
| `protect_unit_deletion()` | 回の編集は全員に許しつつ、`deleted_at` の変更だけを作成者に限定する。行レベルセキュリティのポリシーは「どの列が変わったか」を区別できないため、トリガーで見張っている |

## 要検討

### 決着したもの

- **ログのマークは個人のしおり。** 他人のマークは見えない。`log_marks(log_id, user_id)` として実装
- **回の削除は作成者のみ。** 追加と編集は参加者全員で同期し、削除だけ作った本人に限る。削除すると全員の画面から消えるが、ゴミ箱に出て復元できるのは作った人だけ

### Q3. 添付ファイルの置き場所の保護（ADDLOG-6）

`file_url` の指す先は Supabase Storage という別の仕組みで、**データベースの行レベルセキュリティは効かない**。
バケットを公開設定にすると、URLを知っている人は誰でもPDFを開ける。研究内容が入る前提なので対策が要る。

非公開バケットにして、閲覧のたびに期限付きURLを発行する形にするのが定石。
実装は [#21](https://github.com/iamhiroyuking/rinko-app/issues/21) の時点で構わないが、方針として合意しておきたい。

なお、ログを削除するとデータベース上の `attachments` 行は連鎖して消えるが、
**ストレージ上のファイル本体は残る**。消す処理を別に書く必要がある。

### Q4. 第N回の番号が重複したときの並び順

番号は手で編集できる仕様なので、第3回が2つできてしまうことがある。
そのときの並び順を何で決めるか（作成日時が古い順で良いか）。
