# このアプリは何か（2026-08-21に置き直した）

## 変えた理由

**輪講はここへ来るための踏み台だった。** 作りたいのは、
**友達と知識を共有し、育てる場**。

対象は輪講に限らない。

- 本の内容
- 授業の記録
- 読書の記録

どれも「ひとりで読んで終わらせず、誰かと分け合って伸ばす」という点で同じ。
輪講はその一形態にすぎない。

## 変わらないもの

**データの持ち方は変えない。** 要件定義の時点で
「将来的に読書記録・授業ノートへ拡張する構想があるため、主エンティティ名は
『輪講』ではなく `Book`」と決めてあり、その判断がそのまま効いている。

| | 新しい枠での意味 |
|---|---|
| `Book` | 本・授業・テーマ。**共有する単位** |
| `Unit` | 章・回・その日の分。**区切る単位** |
| `Log` | 気づき・疑問・要約。**中身** |
| `Membership` | 誰と分け合っているか＋その人だけの状態 |
| `Tag` / `LogMark` | 横断して辿る手がかり／個人の目印 |

設計の原則も変えない。

- **個人の状態と共有の状態を分ける**（本棚の並び・しおりは `Membership` 側）
- **追加と編集は全員に同期し、削除だけは作った本人**
- **未ログインでは何も見えない。共有は招待リンクを渡した相手だけ**

## 変わるもの

### 1. 語彙

輪講の言葉が画面に染み出している。数えたところ、
教材123・輪講25・担当11・「第N回」15箇所。

**どう言い換えるかは未決**（下の「決めること」）。

### 2. 輪講に固有の項目を、はっきり任意にする

`Unit` の `presenter_id`（担当）と `scheduled_date`（日程）は、
**輪講には要るが、ひとりの読書記録には要らない。**

列はどちらも既に `null` 可なので、**データベースの変更は不要**。
画面で「無いのが普通」に見えるようにするだけ。

### 3. ひとりで使う場合が主役級になる

これまでは「3人で共有する」を前提に組んできた。読書記録は
**ひとりで始めて、あとから誰かを招く**流れが自然。

- 招待していない教材で、共有の導線が邪魔にならないこと
- 「2人で共有」の表示が、ひとりのときに欠けて見えないこと

## 決めること

| 論点 | 選択肢 |
|---|---|
| `Book` の呼び方 | 教材 / 本 / ノート / テーマ |
| `Unit` の呼び方 | 回 / 章 / セッション / まとまり |
| 種類ごとに言葉を変えるか | `Book` に種別（本・授業・その他）を持たせ、ラベルを切り替える案。**列が増える** |
| 担当・日程の置き場所 | 常に出す / 輪講のときだけ出す / 入力されたときだけ出す |

**「種類ごとに言葉を変える」は慎重に。** 柔軟になる代わりに、
画面ごとに出る言葉が変わって覚えにくくなる。まずは
**全部に通じる1つの言葉**で足りないかを試す方が安い。

## App Storeに出すなら先に決めること

**アカウント削除の導線が無いと審査に通らない**（ガイドライン 5.1.1(v)）。
今は `logs.author_id → profiles` の外部キーが投稿者名を守るため消せない。
これは「削除した人の記録は残る」という仕様の帰結で、不具合ではないが、
**データの持ち方に関わるのでSwiftを書き始める前に決める**（#145）。
