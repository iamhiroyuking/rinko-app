# 要件定義 v2

v1からの主な変更: ログを独立オブジェクトとして正式採用、アカウント制の導入、目標ペース機能の廃止、削除ポリシーの確立。
画面構成は [screen-flow.md](screen-flow.md)、未決事項は [open-questions.md](open-questions.md) を参照。

## ターゲット
- 研究室で輪講を実施している人
- 教科書・参考書を使って輪講形式で学習しているグループ

将来的には読書記録・授業ノートにも使える形へ拡張する構想があるため、
データモデルの主エンティティは「輪講」ではなく **`Book`（教材）** としている。

## 現状の課題

| # | 課題 | 対応 |
|---|---|---|
| 1 | 輪講がどこまで進んだか曖昧 | 回のステータスと進捗バー |
| 2 | 進度の目安・目標が立っていない | **部分的にのみ対応**（下記参照） |
| 3 | 学んでいることの全体像が掴めていない | 回の一覧と全体進捗 |
| 4 | 学ぶことの目的意識が薄い | 各回の `objective`（この回で学ぶこと） |
| 5 | 問題演習が多く、全員が理解できているか分からない | **未対応**（下記参照） |
| 6 | 新しい概念が続出して復習が追いつかない | ログのマークアップ機能で部分的に対応 |
| 7 | 担当者の予習量に見合う進度が得られていない | 担当者が予習段階でログを投稿して共有できる |

### 課題2について
目標ペース機能（週1回などを設定し実進捗との差分を出す）は**廃止した**。
進捗バーで「どこまで来たか」は分かるが、「予定より遅れているか」は分からない。
運用してみて必要になれば後から追加する。

### 課題5について
理解度の可視化（「わかった / あやしい」の意思表示、メンバーごとの復習回数）は
検討の結果いずれも**採用しなかった**ため、この課題は現時点で未対応。
まずは返信で質問できる形で運用してみて、それで足りなければリアクション機能の追加を判断する。

## MVP機能

| # | 機能 | 課題 |
|---|---|---|
| 1 | アカウントを作成してログインできる | ― |
| 2 | 教材（Book）を作成し、本棚に並べられる | 3 |
| 3 | 招待リンクを発行して他のメンバーと共有できる（編集可／閲覧のみ） | ― |
| 4 | 回（Unit）を作成し、担当者・輪講日・「この回で学ぶこと」を設定できる | 4, 7 |
| 5 | 回のステータス（未着手/進行中/完了）を更新し、進捗が一覧で見える | 1, 3 |
| 6 | 回にログを投稿できる（種別・ページ数・本文・ハッシュタグ・添付） | 5, 6, 7 |
| 7 | ログに返信でき、スレッドとして読める | 5 |
| 8 | ログをマークして後から見返せる | 6 |
| 9 | ハッシュタグのサジェストが出る | ― |
| 10 | 本文・タイトル・ハッシュタグを対象に検索できる | 3, 6 |

### MVPに含めない
- 目標ペースと実進捗の差分表示（廃止）
- メンバーごとの復習回数（廃止）
- ログへのリアクション（要検討）
- PDFだけを一覧するタブ
- 複数の教材を横断した検索
- 検索の絞り込み（発言者・回・期間）
- ログの下書き保存
- オフライン閲覧
- 招待リンクの有効期限・無効化

## データモデル

```
User（利用者）
- id
- email
- display_name        表示名。ログの投稿者として表示される
- created_at

Book（教材）          HomeViewの本棚に並ぶオブジェクト
- id
- title               書名
- cover_image_url     表紙画像
- shelf_status        planned | reading | finished
                      本棚の整理用。ユーザーが手動で変更する
                      （回のステータスからは自動計算しない）
- goal                全体を通しての目標（自由記述）
- created_by          -> User
- created_at

Membership（参加）    誰がどのBookに、どの権限で参加しているか
- id
- book_id             -> Book
- user_id             -> User
- role                editor | viewer
- display_order       HomeViewでの並び順（手動並べ替え用）
- deleted_at          ゴミ箱に入れた日時。null なら通常表示
- joined_at

InviteLink（招待リンク）
- id
- book_id             -> Book
- token               URLに含める文字列
- role                editor | viewer   リンク生成時に選択する
- created_by          -> User
- created_at

Unit（回）
- id
- book_id             -> Book
- order               第N回。並び順の正となる値
- title
- objective           この回で学ぶこと（一言）
- presenter_id        -> User   担当者
- scheduled_date      輪講の日
- status              not_started | in_progress | done
                      参加者なら誰でも変更できる
- deleted_at          ゴミ箱に入れた日時
- created_at

Log（発言・記録）     v1で見送った Exercise を独立オブジェクトとして採用
- id
- unit_id             -> Unit
- author_id           -> User
- parent_log_id       -> Log   返信先。null ならスレッドの先頭
- type                none | preview | question | review
                      デフォルトは none。後から値を追加できるようにする
- title
- body
- page_start          数値
- page_end            数値
- is_marked           重要マーク。後から見返すためのフラグ
- created_at
- updated_at

Tag（ハッシュタグ）
- id
- book_id             -> Book   サジェストは教材ごとに出す
- name

LogTag（中間テーブル）
- log_id              -> Log
- tag_id              -> Tag

Attachment（添付ファイル）
- id
- log_id              -> Log
- file_url
- file_name
- mime_type
```

### 命名についての注意
画面名の `SeminarView` は「ある `Book` に属する `Unit` の一覧」を表示する画面を指す。
エンティティ名は `Book` で統一し、「輪講」は使い方の名前として扱う。

## 削除ポリシー

軽いものは確認ダイアログのみ、重いものはゴミ箱を経由する。

| 対象 | 挙動 |
|---|---|
| ログ・返信 | 確認ダイアログ → **完全削除**。返信も連鎖して消える |
| Book | 確認ダイアログ → **ゴミ箱**（`Membership.deleted_at` を設定）|
| Unit | 確認ダイアログ → **ゴミ箱**（`Unit.deleted_at` を設定）|
| ゴミ箱の中身 | もう一度削除すると完全削除。復元も可能 |

### Bookの削除と共有の関係
- 削除は**自分の本棚から消す操作**であり、作成者かどうかによる区別はない
- 共有されている教材を削除しても、**他のメンバーの本棚には残る**。共有者の一覧からその人がいなくなるだけ
- ゴミ箱から復元すれば、元の教材に戻る
- ゴミ箱から完全削除した後で再び参加したい場合は、**招待リンクをもらい直す必要がある**
- **削除した人が残したログはそのまま残る。** ログは `author_id` で `User` に紐づいているため、
  同じ人が再参加した場合もシステム上は同一人物として扱われ、過去の発言と繋がる
- **参加者が全員完全削除した時点で、その教材と配下のデータをデータベースから削除する。**
  誰からもアクセスできないデータを残さない

> 実装メモ: ログはユーザーから見れば完全削除だが、データベース上は `deleted_at` を持たせて
> 物理削除しない方が事故時に復旧できる。列を1つ増やすだけで済むので、そうしておく。

## 権限

| 操作 | editor | viewer |
|---|---|---|
| 教材・回・ログの閲覧 | ○ | ○ |
| 回の作成・編集・削除 | ○ | × |
| ログの投稿・返信 | ○ | × |
| 回のステータス変更 | ○ | × |
| 招待リンクの発行 | ○ | × |
| 自分の投稿の編集・削除 | ○ | ― |
| 他人の投稿の編集・削除 | × | × |

- 招待リンクを発行するときに `editor` か `viewer` かを選ぶ
- 招待リンクは無期限（有効期限と無効化は将来の検討事項）
- 後から参加した人も過去のログを全て閲覧できる

## 並び順

**HomeView（本棚）**
- 学習中（`reading`）の教材のみを表示する
- 学習予定・学習済みはフィルタを切り替えて表示する
- 並び順は手動（`Membership.display_order`）
- 共有されている教材には複数人アイコンを表示する

**SeminarView（回のリスト）**
- `Unit.order`（第N回）を並び順の正とする
- 手動でのドラッグ並べ替えは行わない。順序を変えたいときは第N回の番号を編集する
- ソートの切り替え: 日付が新しい順 / 日付が古い順 / 番号順（第1回が上）

**UnitView（ログ）**
- トップレベルのログは新しい順（最新が上）
- 返信はスレッド内で古い順（YouTubeやInstagramのコメント欄と同じ）

## 非機能要件

- **同時利用者数**: 10人程度、最大でも研究室規模で50人未満
- **データの重要性**: 高い。学習の積み重ねそのものであり、失われると影響が大きい
- **対応端末**: iPhone / Android / iPad / Windows / Mac。輪講中にも輪講後にも書き込む
- **更新方式**: 画面遷移時に再取得し、新着があれば通知して手動更新を促す方式とする。
  完全なリアルタイム購読は実装が重いため、まずこの形で作り、必要になれば後から上げる
- **秘匿性**: 研究内容が書き込まれうる。**未ログインの状態で中身が見えてはならない。**
  未ログインの人が閲覧するには、招待リンクを受け取って参加する必要がある
- **オフライン**: 対応しない。電波のある環境での利用を前提とする

## 開発の進め方

- コード内の識別子は英語、UIの表示は日本語
- Issueは1機能1つの粒度。着手から完了まで半日〜2日で終わる大きさにする
- ブランチ名は `<種類>/<内容>` のkebab-case（`feat/` `fix/` `docs/` `refactor/` `chore/`）
- PR本文に `Closes #N` を書いてIssueと紐付ける
- テストは進捗率の計算・検索フィルタなどロジックに限定する。UIのテストは書かない
- デザインルールはある程度作ってから精査する
